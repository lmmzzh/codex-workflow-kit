# 为什么会有这套 kit

这个仓库一开始并不是一个公开模板项目。  
它最初只是为了回应我在真实项目里反复遇到的一类协作摩擦。

## 问题长什么样

只要任务开始进入中大型迭代，类似的问题就会不断重复出现：

- 每次开工前都要重新讲一遍上下文
- 高风险链路在动代码之前必须先看边界
- 如果没有干净的 handoff，这一轮成果很容易在下一轮里丢掉
- 单纯补更多 prompt，并不能解决真正的协作问题

真正的瓶颈不是“怎么让模型更聪明”，而是“怎么让工作流在真实代码库里更稳定”。

## 后来怎么改了做法

最后落下来的，是一个三层结构：

1. 仓库级规则
2. 长期协作 memory
3. 很少量、可重复的 workflow skills

这里最关键的判断是：

- 长期规则继续留在 memory
- 只有稳定、边界清楚的流程才做成 skill
- 高风险决策继续保留人审

## 为什么默认 skill 只有很少几个

第一批真正有价值的默认 skill，故意只保留了很少几个：

- `current-task-capsule`
- `high-risk-preflight`
- `handoff-retrospective`

这 3 个刚好覆盖了最常见的协作成本：

- 中大型任务开工前先把上下文收住
- 高风险改动前先把边界和最小安全方案看清
- 每一轮实现结束后都能继续接上

像多语言铺开、Figma 页面家族规划这种专项工作流，第一阶段先按需调用，不急着升成默认动作。

## 为什么还要做验证和维护

skill 不是写出来就算有价值。  
它必须先证明自己在真实任务里真的有帮助。

所以这个仓库才会额外带上：

- 自动触发验证清单
- skill 维护规则

这里追求的不是“收集很多 skill”，而是“把很少的一层本地工作流，真正跑顺”。

## 这个仓库真正想提供什么

这套 kit 更适合那些希望 coding agent 变得：

- 更可预测
- 更可复用
- 更容易恢复上下文
- 在高风险区域更不容易乱改

它不是想做一个全自动 agent 平台。  
它只是想把一套更保守、但确实在项目里跑过的协作方式，整理成别人也能复制和改造的版本。
